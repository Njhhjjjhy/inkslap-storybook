# Accessibility

The Inkslap brand targets **WCAG 2.1 AA** as its baseline. The live-site audit revealed multiple pairs that fail this bar today — see **Audit → Findings** for the catalogue. This page documents the standard the brand commits to going forward.

## Colour contrast

### Approved pairs

These pass WCAG AA on white surfaces:

| Foreground | Background | Ratio | Use for |
|------------|------------|-------|---------|
| `#040404` (primary text) | `#FFFFFF` | 19.4:1 | Body, headings, default text |
| `#666666` (secondary text) | `#FFFFFF` | 5.7:1 | Captions, microcopy |
| `#FFFFFF` (white) | `#0099DE` | 3.3:1 | Footer text, button labels — **large text only** (3:1 passes) |
| `#040404` | `#FFA81B` | 9.1:1 | Sparkle backgrounds |
| `#040404` | `#FFDD76` | 12.7:1 | Active-tab highlight |
| `#FFFFFF` | `#D03131` | 5.2:1 | Error states |

### Pairs that fail AA — restricted use

These do not pass AA for body text. They are documented because they exist on the live site, but their use is restricted:

| Foreground | Background | Ratio | Restriction |
|------------|------------|-------|-------------|
| `#999999` | `#FFFFFF` | 2.85:1 | **Decorative only.** Not for body text. Use for non-essential metadata that has a more accessible alternative nearby. |
| `#0099DE` | `#FFFFFF` | 3.3:1 | **Large text only.** OK for buttons (16 px / 600+); not OK for body links. |
| `#0099DE` (footer text on `#0099DE`) | — | — | broken — see below |
| `#F88000` | `#FFEFDF` | 2.7:1 | **Fails everywhere.** Rework the warning tag colour pair. |

### Footer fix

The current footer uses `#FFFFFF` text on `#0099DE` (3.3:1). For body-size copyright and nav labels, this is below 4.5:1. The fix: either use white text at a larger size (≥ 18 px / 600 to qualify as "large") or use a darker shade of blue.

## Touch targets

Every interactive element must be at least **44 × 44 px** (WCAG 2.5.5).

The live site fails this on several elements:

| Element | Current | Target |
|---------|---------|--------|
| Header login / register | 37 × 21 | 44 × 44 |
| Header cart icon | ~24 | 44 × 44 hit area (icon can be smaller, the button isn't) |
| Search input | 26 tall | 44 tall |
| Hero arrows | 40 × 40 | 44 × 44 |
| Colour swatches | 20 × 20 | 44 × 44 hit area (visible swatch can stay 20 × 20) |

**The visible glyph and the hit area are not the same thing.** A 20 × 20 swatch can have a 44 × 44 invisible hit area around it via padding.

## Focus indicators

Every focusable element must show a visible focus state. The documented ring is:

```css
:focus-visible {
  outline: none;
  box-shadow: var(--shadow-focus);
  /* 0 0 0 2px #FFFFFF, 0 0 0 4px #0099DE */
}
```

A 2-pixel white gap then a 2-pixel brand-blue ring. This works on every background — light or dark — because the white gap creates separation from any surrounding colour.

The live site does not consistently show focus rings today. This is a roadmap item.

## Keyboard navigation

Every interactive element must be reachable via keyboard and operable without a mouse.

| Key | Action |
|-----|--------|
| `Tab` | Move to next focusable element |
| `Shift + Tab` | Move to previous focusable element |
| `Enter` / `Space` | Activate buttons, links |
| `Escape` | Close modals, dismiss dropdowns |
| `Arrow keys` | Navigate within components (radio groups, sub-nav tabs, gallery) |
| `Page Down` / `Page Up` | Scroll viewport |

### The nav-link problem

The most consequential a11y finding on the live site: **the header and footer nav items are bare `<li>` elements with no `<a>` wrapper.** Three of them work via inline `onclick`; the fourth (`文章消息`) has neither.

**Fix:** every nav item must be an `<a>` with a real `href`. This:

- Allows keyboard tabbing.
- Allows right-click "open in new tab".
- Is announced as a link by screen readers.
- Is crawlable by search engines.

## Semantic HTML

Use the correct element for the correct purpose:

```html
<!-- Right -->
<a href="/products">All products</a>
<button type="button">Upload your logo</button>
<nav aria-label="Primary">...</nav>
<main>...</main>
<h1>Page title</h1>

<!-- Wrong -->
<li onclick="navigate('/products')">All products</li>
<div role="button" tabindex="0">Upload your logo</div>
<div class="main">...</div>
<div class="page-title">Page title</div>
```

## ARIA

Provide ARIA labels when visual meaning is not clear from the rendered text.

```html
<!-- Icon-only button -->
<button aria-label="Close dialog">
  <CloseIcon />
</button>

<!-- Form field with helper text -->
<label for="email-input">Email</label>
<input id="email-input" type="email" aria-describedby="email-helper" />
<span id="email-helper">We use this for order confirmations.</span>

<!-- Search input -->
<input type="search" aria-label="Search products" placeholder="Search" />
```

---

## Live regions

Announce dynamic content changes:

```html
<!-- Order placed -->
<div role="status" aria-live="polite">
  Order placed. Confirmation sent to hello@yourcompany.com.
</div>

<!-- Form error -->
<div role="alert" aria-live="assertive">
  Unable to place order. Try again.
</div>
```

## Language and screen readers

- `<html lang="en">` on English routes; `<html lang="zh-TW">` on Chinese routes.
- Mixed-script content: `<span lang="zh-TW">...</span>` around Chinese fragments inside an English page (and vice versa).
- The current `/en` route claiming English while serving Chinese content is **broken** for screen readers — speech engines select the wrong voice.

---

## Forms

Every input must have a visible `<label>`. Placeholder-only labelling fails WCAG 1.3.1 and 3.3.2.

```html
<!-- Right -->
<label for="email">Email</label>
<input id="email" type="email" placeholder="name@company.com" />

<!-- Wrong -->
<input type="email" placeholder="Email" />
```

Required fields are marked with an asterisk and `aria-required`:

```html
<label for="password">
  Password <span aria-hidden="true">*</span>
</label>
<input id="password" type="password" aria-required="true" aria-describedby="password-help" />
<span id="password-help">At least 8 characters, letters and numbers.</span>
```

## Motion and animation

Respect `prefers-reduced-motion`. See **Foundations → Motion** for the implementation.

For motion that can't be paused (auto-rotating hero, marquee), provide a pause control or auto-pause when the user has expressed reduced-motion preference.

## Image alt text

Alt text should describe **what the image communicates**, not what the image is.

| Element | Good alt | Bad alt |
|---------|----------|---------|
| Hero with custom mug photography | `Upload your logo to design a custom mug` | `Inkslap logo on a mug` |
| Partner logo in trust strip | `Sotheby's` (the brand name only) | `Logo of Sotheby's auction house` (over-described) |
| Decorative icon next to text label | `""` (empty, marked decorative) | `Cart icon` (redundant with adjacent label) |
| Product photo on a card | `Electroplated ball pen, gold, with company logo` | `Pen` |

Decorative imagery uses `alt=""` and `aria-hidden="true"`.

## Pre-launch checklist

- [ ] Every interactive element has a visible focus ring.
- [ ] Every interactive element is reachable by `Tab` and operable by `Enter` / `Space`.
- [ ] Every form input has a visible `<label>`.
- [ ] Every image has a meaningful `alt` (or empty alt for decoration).
- [ ] Every modal has `Escape` close + traps focus while open.
- [ ] All text meets 4.5:1 contrast (3:1 for large text).
- [ ] No text rendered below 11 px on any breakpoint.
- [ ] `<html lang>` matches the rendered content's language.
- [ ] `<lang>` attributes wrap inline mixed-script content.
- [ ] All animations respect `prefers-reduced-motion`.
- [ ] Headings follow `h1` → `h2` → `h3` order with no skips.
- [ ] Live regions announce dynamic content (order placed, validation errors).
